# 本地 Agent 真正缺的不是模型，而是证据门

很多个人 Agent 的演示都很相似：用户写一个目标，模型生成一段计划，界面把计划显示出来。

问题是，演示结束后我们通常不知道三件事：

1. 这段建议引用了哪一条用户输入？
2. 模型失败时系统还能不能完成闭环？
3. 建议、文件和运行结果发生变化后，原来的结论还能不能复算？

如果答案都是“看不出来”，系统就更像一次性的生成界面，而不是可以被信任、维护和审计的软件。

## 建议不是结果

在个人决策场景里，“建议”很容易被误写成“事实”。

模型可能说“你已经完成了项目”，但它只看到一条被采纳的任务；模型也可能说“这个计划会提高效率”，但系统根本没有测量过效率。

Q-One 的约束是：

- 采纳建议只创建一个待办，不等于执行，也不等于目标完成。
- 推荐必须引用已有目标或任务的候选 ID。
- 推荐记录保留输入 SHA-256、来源和 proposal SHA-256。
- 模型输出不合格时，页面明确显示规则建议和失败原因。

这条边界看起来不“智能”，但它避免把生成文本混成行动结果。

## 没有模型也必须能完成闭环

消费级软件不能假设用户愿意先下载 640MB 权重，也不能假设每次推理都能成功。

Q-One 因此保留两条路径：

- 规则路径：根据目标、任务、时间预算和已有观察生成确定性的行动草案。
- 本地模型路径：固定版本的 Qwen3-0.6B 在随机回环端口提供 OpenAI-compatible 接口，模型只能细化已有候选。

模型缺失、下载失败或结构化输出不合格时，系统回退到规则建议。回退不是隐藏错误，而是以稳定状态和可操作文案显示出来。

## Trace 比“看起来合理”更重要

一次推荐至少要能回答：

- 推荐对应哪个目标？
- 使用的是什么来源：`rules` 还是 `local:Qwen3-0.6B-Q8_0`？
- 输入快照是什么？
- 推荐内容是否被再次修改？

Q-One 的推荐对象包含 `candidate_id`、`input_sha256` 和 `proposal_sha256`。这些字段不证明建议正确，但能让“这次建议是怎么来的”变成可检查的工程事实。

在论文和 Research Factory 场景中，同样的原则进一步扩展为 claim ledger：每条数字或因果论断需要绑定证据位置、文件哈希和复算命令。当前系统阻止了 85 个未闭合 claim 进入发布候选。

这并不意味着论文已经可发表。它只意味着：**证据不足的内容没有因为“项目跑起来了”而自动变成科学结论。**

## 桌面端也必须是一条失败路径

本地优先不等于把服务启动在 `localhost`。

Q-One Desktop 的边界包括：

- Python sidecar 只监听随机回环端口。
- Electron 每次启动生成一次性 256 位 capability。
- 所有 `/api/*` 请求，包括 GET，都需要 capability。
- Renderer 使用 `contextIsolation`，关闭 `nodeIntegration`，只能调用最小 preload API。
- sidecar 崩溃最多重启两次，之后显示可操作错误页。

备份则使用随机数据密钥和 AES-256-GCM；恢复密钥通过 Argon2id 包装数据密钥。恢复先写入 staging 数据目录，验证成功后才切换，失败保留原数据。

这里有一个必须写清楚的限制：工作 SQLite 数据库不是端到端加密。它依赖操作系统 ACL，备份容器才是加密边界。如果把两者混在一起宣传，技术边界就失真了。

## 一个很小的工程验收集

为了避免只展示一次成功，Q-One 增加了 6 个固定任务：

- 写 README 第一页。
- 准备论文统计检查表。
- 规划一周 Python 学习。
- 验证加密备份恢复。
- 起草 200 字基金摘要。
- 整理五份用户访谈。

同一组任务分别跑规则路径和真实 Qwen3-0.6B 路径，记录目标匹配、trace 绑定、可执行步骤、延迟和 Electron 工作集。

当前 Linux x64 CPU 结果：

| 路径 | 目标匹配 | trace 绑定 | 可执行步骤 | 平均延迟 |
|---|---:|---:|---:|---:|
| 规则 | 6/6 | 6/6 | 6/6 | 55ms |
| 本地模型 | 6/6 | 6/6 | 6/6 | 4,540ms |

这组数据只说明当前机器上的六任务工程验收通过。它不证明推荐质量优秀，也不证明用户会因此获得更好的生活或工作结果。

## 证据门不是悲观主义

“无法验证就拒绝发布”听起来会拖慢产品，但它实际上降低了三种常见风险：

- 演示能跑，换一台机器不能安装。
- 模型偶尔能生成，失败后整个流程无法继续。
- 文档里的数字来自手抄，代码或数据更新后没人知道是否还成立。

消费级 Agent 最终要面对的不是一次演示，而是长期使用的本地数据、升级、恢复和故障。

所以 Q-One 的核心不是“让模型说更多”，而是：

> 每条建议知道自己的来源；每次失败有退路；每个对外结论都能被重新计算。

这比多接一个模型更难，也更像真正可以交付的软件。
